# Decipher Survey Base Generator

A local-network tool that converts a formatted questionnaire into a validated base
Decipher XML structure, leaving complex programming to the survey programmer.

**Status: Phase 1 — DOCX parser + formatting extraction.**

The parser is deterministic and is the source of truth for formatting. Later phases
add the local AI classifier, the intermediate survey model and XML generation on
top of the document model this phase produces.

---

## Quick start

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
./run.sh
```

Then open <http://localhost:8000>. The server binds `0.0.0.0` by default, so other
machines on the local network can reach it at `http://<your-ip>:8000`.

| URL       | What it is                                    |
|-----------|-----------------------------------------------|
| `/`       | Upload a questionnaire and inspect the parse   |
| `/docs`   | Interactive OpenAPI docs                       |
| `/health` | Liveness check                                 |

### Without the server

```bash
.venv/bin/python -m app.cli questionnaire.docx --summary   # readable outline
.venv/bin/python -m app.cli questionnaire.docx > parsed.json
```

### Tests

```bash
.venv/bin/python -m pytest
```

The sample questionnaire is generated by `tests/fixtures/build_fixture.py` rather
than committed, so its formatting intent stays readable in the diff.

## What the parser extracts

`POST /api/parse` returns a `ParsedDocument`:

```jsonc
{
  "source_filename": "questionnaire.docx",
  "blocks": [ /* paragraphs and tables, in document order */ ],
  "questions": [ /* detected question boundaries, referencing block indices */ ],
  "stats": { "questions": 4, "tables": 1, "bold_runs": 8, "italic_runs": 5, "…": 0 },
  "warnings": [ "Duplicate question label 'Q1' appears 2 times." ]
}
```

### Paragraphs and character-level formatting

Each paragraph carries its text plus the **runs** that make it up. A run is a
stretch of text sharing one set of formatting, matching the shape the workflow
document specifies for the intermediate survey model:

```jsonc
{ "text": "purchased", "bold": true, "italic": false, "underline": false }
```

Formatting is resolved the way Word resolves it — direct run formatting, then the
character style chain, then the paragraph style chain, then document defaults — so
text that looks bold because of its *style* is reported as bold. Adjacent runs with
identical formatting are merged, because Word splits runs for reasons that have
nothing to do with appearance (spell-check state, revision ids, language tags).

Two cases `python-docx` alone gets wrong are handled explicitly:

- **Hyperlinked text.** Runs inside `w:hyperlink` are not in `Paragraph.runs`;
  without special handling, hyperlinked question text vanishes.
- **Tracked deletions.** Runs inside `w:del` are text the author removed, and are
  excluded.

### Tables

`Document.paragraphs` and `Document.tables` are separate sequences in `python-docx`,
which loses the interleaving between them — and a grid's table has to stay attached
to the question stem above it. The body XML is therefore walked directly, so blocks
come back in true reading order. Cells record `grid_span` and `v_merge` for merged
grid headers, and cell content is parsed recursively (nested tables included).

### List numbering

An auto-numbered option list stores nothing in the paragraph text: the `1.` `2.` `3.`
a programmer sees live in `numbering.xml`. Losing them would mean losing the option
values, so Word's counters are replayed as the document is walked, producing a
rendered `marker` per list paragraph (`decimal`, `lowerLetter`, `lowerRoman`,
bullets, and multi-level `%1.%2` patterns).

Markers typed literally into the text (`1. Price`) are reported separately as
`literal_marker`, since the two need different handling downstream.

### Question boundaries

Boundary detection answers *where each question starts and stops* — not what kind of
question it is. Classification is the local AI's job in Phase 3; keeping the two
apart is what lets the parser stay deterministic.

Recognised label styles include `Q5.` `Q5)` `Q5:` `Q5 -` `[Q7]` `QS1.` `S2.` `D3.`
`Q10a.` `Q5_1.` and `Q 12.`. Each question owns the blocks that follow it until the
next label; content before the first label becomes a `preamble` segment.

`title_runs` gives the question title with the label prefix removed **and the
formatting of the remainder intact** — that is what Phase 2 consumes.

If a document uses no prefixed labels at all, detection falls back to plain `1.` /
`2)` numbering and emits a warning. The fallback is suppressed when prefixed labels
exist, and skips Word-numbered list items, so numbered options are not mistaken for
questions.

```
  config.py                     Settings (env-overridable)

  api/routes_parse.py           POST /api/parse

```

## Configuration

All optional, via environment variables:

| Variable                 | Default | Purpose                                  |
|--------------------------|---------|------------------------------------------|
| `DECIPHER_HOST`          | `0.0.0.0` | Bind address                            |
| `DECIPHER_PORT`          | `8000`  | Port                                     |
| `DECIPHER_MAX_UPLOAD_MB` | `25`    | Upload size limit                        |
| `DECIPHER_KEEP_UPLOADS`  | unset   | Write uploads to `uploads/` (off by default — questionnaires are client-confidential) |
| `DECIPHER_CORS_ORIGINS`  | unset   | Comma-separated origins; not needed for same-origin use |

## Why FastAPI rather than Streamlit

The workflow document suggests Streamlit for the first prototype. FastAPI is the
better fit here because the later phases need a real HTTP API — the review UI in
Phase 5 has to read and *write back* programmer overrides, and Phase 4's XML
generation is naturally an endpoint. Streamlit would have to be replaced at that
point; FastAPI carries forward, and still serves a plain HTML page today with no
frontend build step.

## Known limitations

These are honest boundaries of Phase 1, not defects:

- **Numbering is reported faithfully, not helpfully.** If a questionnaire uses one
  continuous Word list across several questions, options are numbered 5–8 rather
  than 1–4, because that is what the document actually renders. Restarting per
  question is a pre-processing decision for Phase 3.
- **Trailing content attaches to the last question.** A closing "Thank you."
  paragraph belongs to the final question's block range; separating it requires
  semantic understanding.
- **No question classification.** Nothing here decides radio vs. checkbox.
- **DOCX only.** PDF and plain text are listed as later additions in the workflow.
- **`.doc` is not supported** — only the modern zip-based `.docx` format.
